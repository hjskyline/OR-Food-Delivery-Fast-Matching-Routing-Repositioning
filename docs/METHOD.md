# 调度算法与重定位流程

`code/` 是最终分配与路径规划基准；`repositioning/` 在独立实现中增加需求预测和重定位。两者均是离线事件驱动仿真。

1. 读取订单、校验时间顺序并去重；默认根据历史 `courier_id` 和最早抓单位置构造骑手池。历史活跃度用于挑选骑手，默认全部入选骑手从仿真起点上线。
2. 时间跳转至下一订单发布、骑手上线或路线到站事件；完成取送餐、更新位置与容量。
3. 新订单按截止时间排序，形成顺路、低负载和早取餐混合候选集。
4. 枚举有限取送餐插入位置，保证容量与取餐先于送餐；正在前往的下一站冻结。
5. 在准时保护约束下比较系统目标增量，必要时扩大高风险订单搜索；成本超过未服务惩罚时可主动拒单。
6. 同一事件时刻分配完成后，对预计迟到且至少持有三单的骑手进行最多两轮局部路线修复。
7. 重定位实验按配置的决策间隔更新分区需求与供给。默认因果 Gamma-Poisson 预测只使用当时已释放订单；时衰减商家热点、分区服务容量和贝叶斯平滑迟到风险共同决定移动是否值得。
8. 重定位受距离、行驶时间、源分区预留人数、调动比例、冷却时间和预期收益门槛限制。最新代码还会为即将完成服务的骑手安排可取消的后续重定位计划。
9. 骑手移动消耗真实仿真时间和距离，移动途中被分配订单时使用插值位置。`zone_id=-1` 不成为重定位目标，噪声记录的供需归属按代码中的最近合法分区处理；Gamma-Poisson 估计另有有效需求掩码。
10. 输出逐单、逐骑手、重定位事件、核心指标和参数。GitHub 仅保存汇总指标与参数，详细输出在本地生成。

`perfect_horizon_benchmark` 是使用未来订单的理想信息对照，必须与默认在线可用的 `causal_gamma_poisson` 分开报告。即便使用因果需求预测，固定分区标签与骑手池仍来自预处理历史数据，不能由此认定整个实验部署过程完全不存在历史信息依赖。

原始各版本 README 保存在实现目录或 `docs/original/`。部分文字对应较早实验阶段；最新默认参数应以各自 `run_baseline.py --help` 和 `baseline.py` 为准。
